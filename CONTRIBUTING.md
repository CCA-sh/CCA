# Contributing to CCA

Thanks for helping improve CCA. Bug reports, fixes, docs, and new features are all welcome.

By participating you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
To report a security vulnerability, follow [SECURITY.md](SECURITY.md) instead of opening an issue.

## Before you start

- **Bugs:** open an issue with the command you ran, what you expected, what happened, your
  OS, Python version, and model selector (for example `anthropic:claude-sonnet-4-6`).
  Redact API keys and private paths from logs and traces.
- **Features and larger changes:** open an issue first so we can agree on the approach
  before you spend time on it. Small fixes can go straight to a pull request.

## Development setup

CCA uses [uv](https://docs.astral.sh/uv/) and Python 3.11+.

```bash
git clone <your fork>
cd cca
uv sync --extra dev --extra observability
uv run cca --help
```

`pip install -e ".[dev]"` in a virtual environment works too, but `uv.lock` is what CI tests against.

## Running tests

```bash
uv run pytest -q
```

The suite runs offline. A few integration tests call the real Gemini API; they are skipped unless
`GOOGLE_API_KEY` is set (or a Google key is configured in `~/.cca/config.yaml`), and they spend
real tokens when they run.

Source lives under `src/cca/` and tests under `tests/`. Every behavior change needs a test that
fails without the change.

## Code style

- Use descriptive names so intent is clear without comments.
- Comment only when the *why* is not obvious: a hidden constraint, a subtle invariant, a
  workaround. Do not describe what the code does.
- Give every file a one-line docstring describing what it does.
- Prefer small, focused functions; if core logic needs more than two levels of indentation,
  consider splitting it.
- Match the style of the surrounding code.

## Changing tools, models, or docs

- **Built-in tools:** the public tool count is generated from the tool catalog. After adding or
  removing a tool, run `uv run python -m cca.sync_tool_count`; a test fails if the count is stale.
- **Model catalog:** `src/cca/llm/catalog/data/` is generated by `scripts/generate_model_catalog.py`
  from an [oh-my-pi](https://github.com/can1357/oh-my-pi) checkout. Edit the script and regenerate
  rather than hand-editing the generated JSON.
- **Docs:** user documentation lives in `docs/public/` and is published on the website. Update it
  in the same pull request as the behavior it describes. To preview the site:

  ```bash
  cd website
  npm ci
  npm run dev
  ```

## Commits and pull requests

- Write commit subjects in the conventional style used in the history, for example
  `fix: retry a refused --json-schema formatting call` or `feat(instructions): load AGENTS.md`.
- Add an entry under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md), in **Added**,
  **Changed**, **Fixed**, or **Removed**, written for users rather than reviewers.
- Keep each pull request focused on one change, and describe what changed and how you tested it.
- CI must pass: the test suite on Python 3.11–3.13, the package build, `pip-audit` on `uv.lock`,
  and `npm audit` plus the website build.
- If you change dependencies, update the lockfile (`uv lock`, or `npm install` in `website/`) and
  commit it with the change.
